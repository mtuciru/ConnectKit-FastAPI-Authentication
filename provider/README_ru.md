# ConnectKit-FastAPI-OAuth2

Данная библиотека реализует бэкенд составляющую сервера авторизации и типовой фронтенд (можно заменить своим).

Спецификация OAuth 2.0 описывает унифицированный способ авторизации клиентов третьих лиц
для совершения действий от лица пользователя или от своего лица, оставляя при этом на усмотрение разработчиков
механизм авторизации пользователя на самом сервере авторизации или в системе в целом
(если функция провайдера OAuth является только одной из функций).
В результате может возникнуть сложность в обеспечении корректной работы системы,
которой необходимо сочетать работу с собственными сессиями пользователей и сессиями, инициированными клиентами
от лица пользователей.

Идея данной библиотеки лежит в создании единого пространства, обеспечивающего авторизацию и пользователя в системе
напрямую, и сторонних клиентов самостоятельно или от лица пользователя,
и серверов ресурсов, к которым могут обращаться и пользователи, и клиенты.

Поскольку больше всего ограничений вносит именно спецификация OAuth 2.0,
они взяты за основу реализации собственной аутентификации и авторизации пользователя.

Архитектура системы предполагает наличие фронтенд SPA-like приложения, которое посредством javascript
взаимодействует с API провайдера, осуществляя функции входа пользователя, управления аккаунтом и авторизации клиентов.

Аутентификация пользователя может быть внутренней и внешней.

#### Внутренняя аутентификация в один или два этапа (по умолчанию):

Пользователь вводит на странице свой логин (логин, почта или телефон, в зависимости от настроек) и пароль.
Страница делает POST запрос на метод /api/oauth/token c client_id==frontend и grant_type==password.
В ответе сервера будет access_token для доступа (надо добавлять в заголовок Authorization)
и опционально сообщение об ожидании прохождения дополнительного метода аутентификации (mfa).
Реализация библиотеки не требует прохождения ВСЕХ доступных дополнительных методов аутентификации, только одного из.
Однако на конечных эндпоинтах вы можете самостоятельно требовать прохождения конкретных методов,
пройденные методы сохраняются в поле amr сессии.

Методы аутентификации, требуемые на первом этапе и на втором, определяются полями login_via и mfa_via.
Оба поля являются списками значений, разделёнными пробелами,
определяющими один из возможных методов авторизации на этапе. Соответственно, пользователь может выбирать из них.
Также существует поле reauthenticate_via, позволяющее определять методы,
разрешённые для реаутентификации пользователя, если она требуется. По умолчанию, допустимы любые методы из списка amr.

В данной библиотеке реализован главный метод авторизации по паролю и дополнительный через otp код.

Вы можете реализовать любые методы, какие вам необходимо, и требовать их прохождения посредством полей
login_via и mfa_via. Обратите внимание, что если mfa_via не пустой список,
авторизация по паролю всегда будет требовать прохождения второго этапа.
Вы также можете реализовать подобную логику, поставив флаг mfa_waiting для сессии.

#### Внешняя аутентификация:

Внешняя аутентификация выполняется посредством OpenID Connect авторизации на другом провайдере.
OpenID Connect это расширение OAuth 2.0, предоставляющее унифицированный вариант получения информации о пользователе.
Таким образом, составляя информацию от внешнего провайдера с данными пользователей в системе, осуществляется вход.

Состояния, в которые приходит система при использовании внешней аутентификации
(обратите внимание, если почта или телефон не подтверждены в системе или во внешнем провайдере
они в поиске не участвую, так как не доверенные):

1. Пользователь, с соответствующими логином, почтой или номером телефона в системе не найден.

   В этом случае система вызывает зарегистрированный обработчик для вызова страницы регистрации
   (если таковая предусмотрена вашей реализацией) или возвращает ошибку "Пользователь не найден"

2. Найдено зарегистрированное совпадение для пользователя.

   Зарегистрированное совпадение, это заранее выполненное действие "Включить вход через",
   которое сопоставляет данные пользователя внутреннего и внешнего.
   Без включения входа для уже существующего пользователя мы не можем гарантировать,
   что внешний пользователь и внутренний идентичны.

### Структура токена

Токены, создаваемые во всех случаях, имеют одну и ту же структуру,
которая может ссылаться на сессию одного из трёх типов:

1. Сессия провайдера. Это основной тип сессий внутри системы. Пользователи имеют свои scope (определены в таблице)
   Помимо scope ваше приложение должно реализовывать правила, определяющие возможность того или иного действия,
   так как задача scope лишь ограничить область действия
   (например, user:read не определяет, каких пользователей мы можем читать, только общее разрешение на чтение).
   Данный тип сессий генерируется и для transparent клиентов. Это особый тип клиентов,
   которые являются альтернативой браузерной странице провайдера, то есть, взаимодействуют с его API в той же манере.
   Единственное, почему данный тип клиентов существует, чтобы можно было отслеживать сессии,
   созданные через такие клиенты, и изменить ряд параметров. grant_type для таких клиентов разрешён только один:
   password.

2. Сессия клиента, авторизованного для пользователя.
   Данный тип сессий стандартный для OAuth 2.0 и является дочерним по отношению к первому типу.
   Если у клиента нет scope значения 'offline_access', при выходе пользователя из системы (или при истечении сессии
   пользователя)
   сессия клиента также будет закрыта. Если offline_access предоставлен, сессия не будет закрыта.
   scope токена в данном случае является разрешённым подмножеством из всех scope пользователя.

3. Сессия клиента.
   Данный тип сессий предназначен для самих клиентов для их авторизации в системе.
   Это могут быть микросервисы вашей системы или серверы ресурсов, которым необходимо проверять токены доступа
   (провайдер не должен распространять информацию о токене тем, кому она не предназначена).

Данная библиотека предполагает использование в следующих вариантах:

- Выделенный провайдер.

  Выделенный провайдер выполняет только операции с пользователем, что позволяет создать надёжный центр авторизации.

  В данной конфигурации создаваемый сервис будет выполнять следующие задачи:

    - Управление аккаунтами пользователя: создание, изменение, удаление, ...
    - Авторизация конечного пользователя
    - Авторизация сторонних клиентов
    - Валидация токенов для клиентов
    - Возврат информации о пользователе

  Сервисы ресурсов должны быть зарегистрированы как client_credentials клиенты и использовать
  методы introspect и, если необходимо, userinfo, для обработки запросов.
  (ConnectKit-FastAPI-OAuth2-Client предоставляет middleware, который автоматически проверяет токены)

- Встроенный провайдер.

  Встроенный провайдер объединяется вместе с ресурсным сервисом, что упрощает систему,
  однако может привести к снижению уровня надёжности системы или её безопасности.

  В данном варианте сервис будет объединять функции провайдера и ресурсного сервиса,
  следовательно, информация о текущем пользователе будет доступна и так.

Основными двумя точками инициализации библиотеки являются методы 'setup_as_provider' и 'setup_as_resource'.
В случае, если реализуется единое приложение fastapi следует вызвать setup_as_provider с объектом конфигурации функций.
В этом случае будет инициализирован middleware проверки аутентификации пользователя и все необходимые эндпоинты.
Обратите внимание, что в данной библиотеке реализована проверка CORS для всех методов, что её требуют,
так что использование CORS middleware может вызвать конфликты.
Вы можете разбить ваш проект на несколько приложений fastapi и соединить их через mount.

Помимо двух точек инициализации существует ряд методов 'set_*' для установки callback функций.
Данные функции будут вызываться в процессе работы для получения необходимой информации.
Например, может быть запрошена расширенная информация о пользователе (его адрес) если таковая есть и доступна к выдаче.

Если необходимый callback не установлен, а информация критична для обработки, клиент получен сообщение об ошибке.
Также сообщение об ошибке будет выдано, если конфигурация некорректна
(например grant_type transparent клиента не равен password), это защита от неправильного использования.

### Функции

Функции делятся на две категории:
Включено всегда и можно включить

#### Включено всегда:

- Эндпоинт /api/oauth/token.
  Через него осуществляется аутентификация пользователя по паролю (grant_type==password).
- Эндпоинт /api/oauth/userinfo.
  Это стандартная точка получения информации о пользователе.
  В случае сессии провайдера, это полная информация об вошедшем пользователе.
- Эндпоинты метаинформации по стандартам OAuth 2.0 и OpenID Connect Discovery.
  По данным путям лежит документ, описывающий текущую конфигурацию системы.
- Гранты password и refresh_token.
- Расширение Proof Key for Code Exchange by OAuth Public Clients
  По умолчанию проверяется, если предоставлено, но можно требовать.
  Работает только для response_type включающего code.
- Расширение OAuth 2.0 Demonstrating Proof of Possession.
  Данное расширение предполагает дополнительный тип токенов
  с подтверждённым владением со стороны экземпляра клиента.
  По умолчанию, данное расширение не обязательное,
  но можно включить его требование для фронтенда или любого клиента.
- Привязка токена к ip.
  Данное расширение действует только для сессий второго и третьего типов.
  Можно включить для клиента, по умолчанию отключено.
- Расширение OAuth 2.0 Step Up Authentication Challenge Protocol.
  Ресурсный эндпоинт может запросить обновить сессию для достижения заданных критериев.
  Значения acr_values и max_age указывают условия, которые должны быть выполнены.

  acr_values -- это требования методам аутентификации пользователя.
  
  max_age -- это требования к тому, когда в последний раз пользователь себя аутентифицировал.

  Сам провайдер может генерировать подобную ошибку, если требуется повторная аутентификация.
